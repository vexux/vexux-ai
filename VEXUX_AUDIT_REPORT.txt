4. API route and fraud-specific call path
-----------------------------------------
CONFIRMED: API
- `api.main.get_agent()` returns `core.composition.create_agent()`.
- `POST /api/v1/agent/run` injects this generic agent through `run_agent()`,
  which calls `agent.run(query, session_id, user_id)`.
- AgentRunRequest accepts optional workflow, agent, and delegations values,
  but `run_agent()` does not forward these fields.
- Generic composition registers KnowledgeGroundedAnswerWorkflow, not
  FraudInvestigationWorkflow. The route does not select the synthetic or
  real fraud composition.
- FastAPI's default interactive documentation route is `/docs`.
- The endpoint emits audit events and redacts some serialized output, but it
  does not authenticate the requestor.

CONFIRMED: synthetic fraud path
- `apps.fraud.demo.create_demo_agent()` calls generic composition, then
  creates a temporary SQLite database seeded from
  `apps/fraud/data/sqlite/demo.sql`, creates in-memory graphs, configures
  FraudPolicy, and registers FraudInvestigationWorkflow.
- Direct call shape: enter the `create_demo_agent()` context, then invoke
  `agent.run("Investigate C1001", user_id="investigator")`.
- `FraudInvestigationWorkflow.plan_query()` maps recognized fraud queries to
  workflow tasks. Planner and ExecutionManager dispatch these to workflow
  execution; the fraud service computes the categorical assessment.
- `Agent.run_workflow()` also invokes a registered workflow, but is not
  wired to the HTTP route.
- `apps.fraud.real.create_real_agent()` is a separate Neo4j/MySQL composition
  and intentionally has no synthetic fallback.

8. Synthetic customer fixture inventory and expected outcomes
------------------------------------------------------------
The following inventory is from the demo's SQLite seed and in-memory graph
factory, not real/customer data. "Expected" outcomes are static deductions
from the fixture rows and `FraudInvestigationService.build_result`; they
were not run during this review.

All customer IDs in the combined demo fixture:
- C1001 — appears in `apps/fraud/composition.py` and
  `apps/fraud/data/sqlite/demo.sql`.
- C1002 — appears in the graph fixture and SQLite seed.
- C2001 — appears in both in-memory graph fixtures only; it has no account,
  transaction, fraud-alert, or investigation rows in the SQLite seed.

Case analysis:
- C1001 — expected HIGH. The SQLite seed provides one open high-severity
  alert (AL1001), one transaction (T1001, 120.0), and one open investigation
  (I1001/F900). The graph connects C1001 to D500, which is also connected to
  C2001. Scoring signals: `open_high_severity_alerts`,
  `shared_device_relationship`, and `active_investigation`. The elevated
  transaction signal does not apply: there is only one transaction and its
  amount is below the aggregate threshold. This matches the user-reported
  actual C1001 result in section 4.
- C1002 — expected MEDIUM. It has two transactions (70.0 and 25.0), one
  low-severity closed alert, and no investigation row. Its D501 device is
  also connected to C2001. Only `shared_device_relationship` should score:
  the two-transaction sum is below 2000, and the alert is neither high nor
  open. One signal gives MEDIUM under the deterministic rule.
- C2001 — expected MEDIUM, with graph-only evidence. It shares D500 with
  C1001 and D501 with C1002. It has no matching SQLite business rows, so no
  transaction, alert, or investigation signals should be added. The
  `LINKED_TO` relationships satisfy the service's shared-device signal
  predicate, leaving one signal and therefore MEDIUM. This assumes the
  complete demo graph registry and demo SQLite fixture are composed as in
  `create_demo_agent()`; this particular case was not executed.

Risk-category coverage in the bundled demo data:
- HIGH and MEDIUM are represented by these three customers.
- No customer in the bundled demo fixture appears to produce LOW: each has
  at least one shared-device relationship, and C1001 also has an open high
  alert and an investigation.
- The scoring implementation can produce LOW for no-signal input, but that
  is not an expected category for any of the three demo fixture customers.

13. Enterprise-approved model service compatibility
----------------------------------------------------
CONFIRMED: current provider seam
- `core.contracts.capabilities.ModelProviderContract` is a structural
  Protocol requiring a `name` property and
  `generate(prompt, response_format=None, **kwargs) -> str`.
- `ModelGateway` accepts that provider, forwards prompt and generation
  kwargs, returns the provider's string, logs success/failure metrics and
  re-raises failures. `provider_metadata()` allowlists provider, model,
  runtime_mode, host, and adapter_path fields; implementations should not
  put credentials, tokens, or sensitive endpoint details in metadata.
- `core.composition.create_agent()` explicitly maps a fixed set of provider
  names to implementations. `core.config.SUPPORTED_MODEL_PROVIDERS` also
  explicitly limits values to fake, ollama, mistral, and qwen. There is no
  provider-plugin discovery mechanism or generic HTTP provider configuration.
- Ollama is lazy-client based; Mistral wraps a chat-completions client;
  Qwen loads its local ML stack at provider construction. All adapt their
  request/response format to the same synchronous string-returning contract.

FEASIBILITY — INFERENCE FROM THE SEAM
- An internally approved HTTP model gateway could be implemented as another
  `ModelProviderContract` implementation and passed to the existing
  `ModelGateway`. The fraud investigation/scoring code need not change just
  to swap text-generation providers: `FraudInvestigationService.build_result`
  computes categorical risk from retrieved deterministic signals, rather
  than asking the provider to score risk.
- To select it through normal app composition, implementation would still
  need a new supported provider identifier, configuration fields, and a
  construction branch in `core.composition.create_agent()` (or another
  explicitly injected provider in the composition root). The existing
  contract alone does not make an unregistered provider selectable.
- The provider must map prompts, response-format requests (including JSON
  where requested), and generation kwargs to the approved gateway's actual
  protocol; validate response shape and text; apply bounded timeouts and
  clear error handling; and avoid logging prompt bodies, credentials, or
  confidential payloads. Compatibility with any actual internal API is
  unknown until its approved contract is supplied and reviewed.

FAKE PROVIDER AS DETERMINISTIC OPTION
- `FakeProvider` remains usable independently of local or remote model
  availability and satisfies the same minimal provider shape. It provides
  deterministic intent/planning/delegation examples and a generic
  `FAKE_RESPONSE` for ordinary prompts; it is not semantically equivalent
  to a production LLM.
- The fake provider is selected explicitly via `MODEL_PROVIDER=fake`.
  `create_demo_agent()` supplies fake only when MODEL_PROVIDER is absent and
  preserves an explicit setting. There is no automatic failover from an
  unavailable enterprise provider to fake. This is appropriate: automatic
  fake fallback could make a real generation failure look successful or
  silently change demo semantics.
- Fake can remain the offline deterministic test/demo mode; if a fallback is
  desired, make the mode visible and explicit, preserve the original
  provider failure in the trace/log, and obtain approval for that behavior.

RAG EMBEDDING COMPATIBILITY
- Current `rag.Embedder` lazily imports `SentenceTransformer` and defaults to
  `BAAI/bge-small-en-v1.5`. `RAGPipeline` accepts an optional embedder object
  with `encode(texts)` and validates that document embeddings are a 2-D
  matrix with one row per chunk. `Retriever` uses the same embedder to encode
  queries. A custom approved remote/local adapter could satisfy this
  duck-typed behavior without changing fraud scoring.
- The standard `core.composition.create_agent()` currently constructs
  `RAGPipeline` without passing an embedder, so the default Sentence
  Transformers path is used if retrieval initializes. No setting for an
  approved embedding endpoint or local asset directory exists in inspected
  configuration.
- A company-approved embedding service would require a separately approved
  endpoint/protocol and explicit injection/wiring into RAG composition. It
  would need to embed both corpus chunks and queries in the same vector
  space, preserve dimensions and normalization/metric expectations, and
  receive only documents/query data authorized for that service.
- A pre-approved local model may be usable by supplying a local model path
  to SentenceTransformer-compatible loading, but this code does not enforce
  local-only loading or demonstrate a bundled/cache-ready asset. Verify
  approved asset provenance and prevent unapproved downloads before use.
- Even with remote embeddings, current retrieval still uses in-process FAISS
  and NumPy (`rag.vectorstore`); replacing those with a hosted vector service
  is a separate adapter/design change. `FakeProvider` generates text and
  cannot substitute for embedding vectors.
- RAG tests demonstrate embedder injection, including deterministic lexical
  embeddings, but no approved enterprise embedding provider or local-asset
  policy is implemented or verified.
