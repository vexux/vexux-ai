2. Llama GGUF provider
----------------------
SOURCE-CONFIRMED
- `models/providers/llama_cpp.py` adds `LlamaCppProvider`, implementing the
  existing synchronous `generate(prompt, response_format=None, **kwargs)`
  behavior without changing `ModelProviderContract` or `ModelGateway`.
- Import of `llama-cpp-python` and model initialization are lazy. Each
  provider instance initializes its model once, guarded by a lock; model
  generations are serialized through a second lock.
- The default expected path is
  `models/weights/Llama-3.2-3B-Instruct-Q4_K_M.gguf`; `LLAMA_CPP_MODEL_PATH`
  and a terminal path option can select a different local file. Missing files
  raise a clear `FileNotFoundError`. Missing `llama-cpp-python` raises a clear
  `RuntimeError`. Neither case falls back to Qwen3 or fake and no download is
  attempted.
- CPU execution is explicit (`n_gpu_layers=0`). Defaults are context 2048,
  four CPU threads, and 256 output tokens, with validated upper bounds of
  8192, 16, and 1024. Caller output limits are capped by the configured
  provider maximum. Default completion settings are deterministic
  (`temperature=0.0`, `top_p=1.0`).
- Chat completion uses a user message and returns the completion text.
  `response_format="json"` adds prompt guidance only; valid JSON is not
  guaranteed. Unsupported formats and invalid inputs/limits are rejected.
- Metadata reports provider `llama_cpp`, local runtime, and only the GGUF
  basename. Configuration diagnostics also return only the basename; the
  custom `Config.__repr__` does not include model paths or secrets.
- `core/composition.py:create_agent()` constructs this provider only when
  `MODEL_PROVIDER=llama_cpp`. Existing providers/default behavior are
  preserved.

- Llama inference was not run. The `.venv` inspection recorded during this
  task found `llama-cpp-python` missing, and no GGUF file was supplied or
