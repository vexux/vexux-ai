2. Llama GGUF provider
----------------------
SOURCE-CONFIRMED
- `models/providers/llama_cpp.py` adds `LlamaCppProvider`, implementing the
  existing synchronous `generate(prompt, response_format=None, **kwargs)`
  behavior without changing `ModelProviderContract` or `ModelGateway`.
- Import of `llama-cpp-python` and model initialization are lazy. Each
  provider instance initializes its model once, guarded by a lock; model
  generations are serialized through a second lock.
- The default expected path is
  `models/weights/Llama-3.2-3B-Instruct-Q4_K_M.gguf`; `LLAMA_CPP_MODEL_PATH`
  and a terminal path option can select a different local file. Missing files
  raise a clear `FileNotFoundError`. Missing `llama-cpp-python` raises a clear
  `RuntimeError`. Neither case falls back to Qwen3 or fake and no download is
  attempted.
- CPU execution is explicit (`n_gpu_layers=0`). Defaults are context 2048,
  four CPU threads, and 256 output tokens, with validated upper bounds of
  8192, 16, and 1024. Caller output limits are capped by the configured
  provider maximum. Default completion settings are deterministic
  (`temperature=0.0`, `top_p=1.0`).
- Chat completion uses a user message and returns the completion text.
  `response_format="json"` adds prompt guidance only; valid JSON is not
  guaranteed. Unsupported formats and invalid inputs/limits are rejected.
- Metadata reports provider `llama_cpp`, local runtime, and only the GGUF
  basename. Configuration diagnostics also return only the basename; the
  custom `Config.__repr__` does not include model paths or secrets.
- `core/composition.py:create_agent()` constructs this provider only when
  `MODEL_PROVIDER=llama_cpp`. Existing providers/default behavior are
  preserved.

1. Current implementation status
--------------------------------
SOURCE-CONFIRMED
- `prod` was checked; the worktree was clean before and after the read-only
  audit.
- `models/providers/llama_cpp.py` implements a lazy local GGUF provider.
  Initialization specifies `n_gpu_layers=0`, `n_ctx=2048` by default, and
  `n_threads=4` by default. It calls `create_chat_completion` with a user
  message, bounds output tokens by the configured maximum (256 by default),
  and serializes model initialization and generation with separate locks.
- The provider accepts context sizes up to 8192, thread counts up to 16, and
  output limits up to 1024. It wraps load/generation errors, but does not
  measure or enforce prompt-token fit against context remaining for output.
- `core/config.py` supports provider `llama_cpp` and reads
  `LLAMA_CPP_MODEL_PATH`, `LLAMA_CPP_N_CTX`, `LLAMA_CPP_N_THREADS`, and
  `LLAMA_CPP_MAX_NEW_TOKENS`. The default path is
  `models/weights/Llama-3.2-3B-Instruct-Q4_K_M.gguf`.
- `core/composition.py` constructs the provider from these config values and
  passes it to `ModelGateway`. The gateway forwards keyword arguments and
  re-raises provider errors.

INFERENCE / UNKNOWN
- This implementation is configured for CPU-only inference. The integrated
  Radeon 760M will not be used by this provider as currently initialized.
- Actual loading, inference, output quality, memory use, and speed on the
  target laptop were not tested. No success claim is made.

2. Confirmed compatibility issues and limitations
--------------------------------------------------
SOURCE-CONFIRMED
- `llama-cpp-python` is absent from both `requirements.txt` and
  `requirements-dev.txt`; it is an optional runtime dependency. Provider
  selection can succeed without loading it, but generation then fails if the
  package is missing.
- No package version or tested Windows/Python combination is pinned in the
  repository.
- `response_format="json"` appends a natural-language instruction; it does not
  configure constrained/grammar-based JSON output. Valid JSON is not
  guaranteed.
- No pre-generation check verifies that prompt tokens plus requested output
  fit `n_ctx`; context overflow may surface as a runtime error.
- Planner/synthesis callers can pass `do_sample=False`. The provider forwards
  remaining keyword arguments to `create_chat_completion`; because no package
  version is pinned and no runtime test was performed, compatibility and
  behavior for this argument are UNKNOWN.
- `tests/unit/test_llama_cpp_provider.py` substitutes a mock `llama_cpp`
  module and a dummy GGUF file. It validates provider logic but not the native
  runtime or a real model.

5. Memory and CPU considerations
-------------------------------
INFERENCE (planning estimate; not measured)
- A 3B Q4_K_M GGUF is typically on the order of 2 GB on disk; exact size for
  the target file is UNKNOWN because the file was not inspected.
- Assuming the usual Llama 3.2 3B architecture and FP16 KV cache, approximate
  KV-cache use is about 0.22 GB at 2048 tokens and 0.9 GB at 8192 tokens.
  Runtime buffers, application memory, Windows, and concurrent workloads add
  to this. The target's approximately 15.28 GB usable RAM appears plausible
  for CPU inference, but peak use must be measured with the approved model.
- Four threads is the configured baseline on the stated 6-core/12-thread CPU.
  The provider allows up to 16, but neither an optimal setting nor inference
  throughput can be concluded without measurement.
- The integrated GPU shares system memory, but it does not provide inference
  acceleration while `n_gpu_layers=0`.
